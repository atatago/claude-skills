# ガバナンス文書の作成と見直し

AI と進めるプロジェクトの判断基準を、憲法・法律・哲学・細則の階層で文書にする。文書だけで守らせようとせず、守られているかを確かめられる形にするのが目的。

## 基本の考え方

- 優先順位は 憲法 > 法律 > 哲学。細則は法律の詳細で、必要なときだけ読む。
- 哲学は2つに分ける。アプリの哲学(何を作るか・どう進めるか)と、設計の哲学(コードの形をどう判断するか)。具体的な決めごと(コーディング規約)は哲学ではなく、言語ごとの細則にする。
- 文書は内側から効かせる(AI が理解して判断する)。仕組み(CI・テスト・スクリプト)は外側から止める。両方を使い分ける。
- 外側で止めるのは「結果として許されない状態」だけにする(公開できないデータ、ライセンス違反、壊れたビルドなど)。やり方・設計・表現は文書で方向を示し、AI の判断に任せる。強制は少なく、太く。
- ルールには、足した理由ときっかけを残す。理由がないと、あとで効いているかを確かめられず、要らなくなっても外せない。
- 文書だけのルールが破られたら、注意書きを足すより先に、仕組みで止められないかを考える。

## ファイルの構成

```
CLAUDE.md                        ガバナンスの3文書を @ で取り込み、細則は「必要なときだけ読む」と場所を書く
docs/governance/constitution.md  憲法
docs/governance/laws.md          法律
docs/governance/philosophy.md    哲学(アプリ)
docs/governance/design-philosophy.md  設計の哲学(コードの形の判断。短く保ち、毎回読む)
docs/governance/coding-<言語>.md  コーディング規約(細則。コードを書くときだけ読む)
docs/governance/<細則>.md        そのほかの細則(ライセンスの台帳など。毎回は読まない)
```

同じルールを2か所に書かない。ルールは法律に置き、CLAUDE.md には手順(コマンド・場所)と、法律の該当章への参照だけを書く。

## 新しく作る

### 1. 聞き取り

決める前に、次を利用者に確かめる(分からないものは「未定」として法律に残してよい)。質問は一度に多くしない。

- 目的と、誰のためのものか
- 第三者のデータ・コード・フォント・画像を使うか(ライセンス)
- 個人情報・広告・計測を扱うか
- 費用の考え方(無料が絶対条件か、努力目標か)
- 公開の方法と、公開前に通すべき確認
- 使う言語・フレームワークと、フォーマッタ・リンター・型チェックなどのツール(規約のうち、ツールで強制できる範囲が決まる)
- AI にどこまで任せ、人がどこを確かめるか(実際に確かめられる範囲で答えてもらう)

### 2. 憲法

何があっても守る原則を5〜8条。目的、正確さ、ライセンス、利用者の尊重、コストの考え方、改正の手続きが基本。実装の話は書かない。改正履歴を末尾に置く。

### 3. 法律

憲法に反しない範囲の具体的なルールを、章ごとに書く(ライセンス、内容の正確さ、データと実装、進め方、広告やプライバシーなど)。

- 冒頭に次の一文を置く: 「条文の末尾の〔仕組み: …〕は、その条文を CI・テスト・スクリプトで確かめていることを示す。印のない条文は文書だけで守っている。」
- 各条文について「機械的に判定できるか」を考える。できるものは仕組みを作るか、作る候補としてタスク一覧に積む。仕組みができたら〔仕組み: …〕を付ける。
- 実態と合わない理想を書かない。たとえば「人が全件確認する」と書くなら、本当に行えるかを利用者に確かめる。行えないなら、実際の確認方法(別セッションの AI のレビューなど)と、その弱さを補うルールを書く。
- 4章(進め方)に「条文を足す・変えるときは、きっかけ(どの作業で何が起きたか)を改正履歴に書く」を入れる。
- 改正履歴を末尾に置き、初版から日付ときっかけを書く。

### 4. 哲学

決まりがない場面の判断の拠り所。5〜10項目、1項目1〜2文。全体に共通の哲学がなければ、このスキルの `templates/philosophy.md` を土台にし、プロジェクトに合わせて足す・書き換える。どのプロジェクトでも、次の2つは残す。

- 繰り返す失敗は仕組みで止める。失敗はまず記録し、同じ種類が繰り返されたら、注意書きより先にチェックや自動化で止められないかを考える。
- ルールには理由を残す。

全体に共通の哲学があるときは、それを土台にし、プロジェクトの哲学で上書きしてよい。

### 4-2. 設計の哲学

コードを書くプロジェクトでは、`templates/design-philosophy.md` を土台に設計の哲学を作る。原則を「守るべき規則」として書かず、いつ効かせるかを含めて書く(規則にすると、小さなコードにまで抽象化が持ち込まれる)。プロジェクトの実際の構成(層の分け方、差し替えの方法など)が分かっていれば、例としてその場所を書き添える。

### 5. 細則

毎回読む必要がない詳しい内容(ライセンスの台帳、外部データの更新手順など)は細則に分け、CLAUDE.md に「いつ読むか」を書く。

コーディング規約は `templates/coding-template.md` を土台に、言語ごとの細則として作る。ツールで強制しているもの(フォーマット・命名・型など)は「どのツールが何を確かめているか」だけを書き、ツールで確かめられない決めごとだけを書く。新しく作るより、既存のコードを読んで、実際に守られている書き方を書き起こすほうを優先する。

### 6. 仕組みとのつなぎ

文書と同時に、次を用意する(またはその計画をタスク一覧に書く)。

- 公開の前に、テストとデータのチェックを必ず通す CI
- チェックの対象は自動で拾う。対象を手で並べる方式(フォルダやファイルを1行ずつ書き足す)は、書き忘れたものが黙って素通りする。
- チェックの方法が決まっていない新しい種類のデータは、素通りさせずに失敗にする(「チェックがないから止まる」)。
- main のルールで必須にしたチェックが、paths-ignore などで起動しない PR がないか確かめる。起動しないと、結果待ちのまま止まってマージできない。PR では常に CI を動かし、節約は push 側だけにする。
- PR の雛形に、法律の主な条文に対応するチェックリストを置く。

### 7. 記録の形

あとで振り返れるよう、最初から記録の形を決めておく。

- AI の成果物のレビューで要修正になったものは、指摘の種類を決まった語で付ける(例「【仕様】【正確さ】【表記】…」)。種類の語はプロジェクトに合わせて5〜8個決め、レビューの手順に書く。
- 失敗から足したルールやチェックには、「v1.2 のリリース作業で漏れていた」のように、きっかけを注記する。

## 見直す(振り返り)

利用者に「見直したい」「効いているか確かめたい」と言われたときの手順。修正の前に方針を示し、確認を取ってから直す。

1. 材料を集める: Git の履歴(修正・レビューのコミット)、法律と哲学の改正履歴、スキルやチェックのスクリプトに残された「〜で漏れていた」などの注記、レビューの記録
2. 指摘や失敗を3つに分ける
   - ルールがあって防げた(効いた)
   - ルールがあったのに破られた(効かなかった) → 書き直すか、仕組みに移す候補
   - ルールがなかった → 新しく書くか検討する
3. 数えるときは合計の率ではなく、指摘の種類ごとに、ルールを足した前後で比べる。合計の率は内容の難しさやレビューの厳しさで揺れる。
4. 結果をドキュメントにまとめる(概要、効いた例、効かなかった例、ルールがなかった例、数字、所見)。数字の出所と限界を書く。
5. 見直しの方針を示す。よく出る候補:
   - 仕組みで確かめている条文に〔仕組み〕の印がない
   - 実態とずれた条文(人の確認、古いスクリプト名など)
   - CLAUDE.md と法律に同じルールが重複している
   - 哲学が初版から更新されていない
   - 設計の哲学やコーディング規約がない、または実際のコードと合っていない
   - レビューの記録に指摘の種類がない
6. 利用者の確認を取ってから修正し、PR にする。改正履歴に、見直しのきっかけ(振り返りの名前など)を書く。

## 注意

- 条文は増やす一方にしない。見直しのたびに、引かれていない条文・破られ続ける条文を確かめる。
- 文書は毎回コンテキストに載るので、長くなるほど効きが薄まる。毎回読む部分は短く保ち、詳細は細則に出す。
- 実際に起きたことに基づいて書く。想像の失敗に備えた細かい条文は、AI の判断の幅を狭める。
