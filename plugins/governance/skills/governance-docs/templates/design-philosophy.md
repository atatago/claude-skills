# 設計の哲学(標準)

コードの形を決めるときの判断の拠り所。規則ではなく、いつ効かせるかを含めた考え方として使う。小さなスクリプトなど、効かせると読みにくくなる場面では無理に当てはめない。
憲法・法律(コーディング規約を含む)と矛盾する場合は、そちらが優先される。プロジェクトに合わない項目は書き換えるか外してよい。

1. **変更の理由で分ける。** 1つの単位(関数・クラス・モジュール)が変わる理由は1つにする。
2. **増えるところは、足すだけで済む形に。** 種類が増えると分かっている箇所は、既存のコードを書き換えずに追加できるようにする(開放閉鎖)。増える見込みのない所には先回りしない。
3. **外の世界は差し替えられるように。** 外部サービス・ファイル・時刻・乱数などには、直接ではなく抽象を通して依存し、外から渡す(依存性の逆転・DI)。テストで差し替えられることを目安にする。
4. **継承より組み合わせ。** 振る舞いの共有は、継承の階層より、小さな部品の組み合わせで行う。
5. **抽象化は繰り返しが見えてから。** 同じ知識は1か所に置くが、たまたま似ているだけのコードは無理にまとめない。3回目で共通化を考える。
6. **意図は名前で伝える。** コメントで補う前に、名前と構造で分かるようにする。

依存の向き(「画面の層からデータの層を直接呼ばない」など)のように機械で確かめられるものは、ここではなく法律かコーディング規約に書き、仕組み(依存関係の検査ツールなど)で確かめる。
